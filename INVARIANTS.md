# SimCom V2.5 - Инварианты системы

Проверяются в `check_invariants()` после каждой инструкции. Нарушение не роняет процесс - ошибки собираются в список, печатаются в `stream_out`, выставляется `CE`, машина останавливается и кидает `InvariantViolation`. Если что-то из этого сработало - смотри сюда.

---

## I-1. Стек

`2 ≤ sp ≤ SS_START`

`SS_START = 171` - пустой стек. Ниже 2 не опускаемся: адреса 0–1 забиты под IVT, затирать их стеком - плохая идея.

После симметричных `PUSH`/`POP` и `CALL`/`RET` указатель обязан вернуться в `SS_START`. Не вернулся - утечка.

```python
sp = self.registers['sp']
if not (2 <= sp <= SS_START):
    errors.append(f'I-1 нарушен: SP={sp} вне диапазона [2, {SS_START}]')
```

**v1.8:** Выпилили промежуточный регистр в `CALL` - он тихо затирал `AX`. Адрес возврата должен лежать строго на стеке, нигде больше.

**v2.5:** Основную защиту границ SS/DS теперь берет на себя `MMU.check_range()` при каждом `PUSH`/`POP` - до того, как SP успеет выйти за диапазон. Этот инвариант - контрольная проверка постфактум, а не единственная линия обороны.

## I-2. Защита кода

В `CS_START ≤ addr < MEM_SIZE` не должно быть числовых значений - только инструкции (список токенов) или пустая строка.

Само право писать в CS блокирует `MMU` еще на этапе трансляции адреса - до этого инварианта дело в норме не доходит. Здесь проверяется постфактум: если число все-таки просочилось в сегмент кода, это не ошибка юзера, а рассинхрон состояния эмулятора.

Проверка через `isinstance` - да, костыль, но зато сразу видно, если в сегмент кода прилетело число вместо инструкции.

```python
for addr in range(CS_START, MEM_SIZE):
    if isinstance(self.memory[addr], (int, float)):
        errors.append(f'I-2 нарушен: числовое значение в CS по адресу {addr}')
        break
```

TODO: этот скан дико тормозит на больших дампах, надо переписать на маску доступа.

**v2.4:** Косвенная адресация `[bx]`/`[si]` могла читать данные за пределами лимита `DS_START + size` - реальный лимит MMU для DS в тот момент был мягче, чем должен. Исправлено в `_ptr_addr`, но этот инвариант остается как последний рубеж на случай похожих регрессий.

## I-3. ALU (16-битная арифметика)

`math_op` режет все до `[-32768, 32767]`. `OF = 1` - было обрезание. Флаг выставляем для совместимости, по факту на него никто особо не смотрит.

```python
for reg in GP_REGS:
    val = self.registers[reg]
    if not (-32768 <= val <= 32767):
        errors.append(f'I-3 нарушен: {reg.upper()}={val} вне [-32768, 32767]')
```

**v1.2:** `ZF` не сбрасывался после `MOV`. Граница между ALU и data transfer была размытой, поймали случайно.

## I-4. Указатель инструкций

`CS_START ≤ ip < MEM_SIZE` пока `is_run = True`

Прыжок за пределы CS ловится через `MMU.translate()` раньше, чем IP успевает записаться неправильным значением - этот инвариант проверяет, что защита реально сработала. После `END` значение IP не проверяем.

```python
if self.is_run:
    ip = self.registers['ip']
    if not (CS_START <= ip < MEM_SIZE):
        errors.append(f'I-4 нарушен: IP={ip} вне CS [{CS_START}, {MEM_SIZE})')
```

**v1.7:** `LOOP` с `CX = 1` прогонял тело лишний раз - порядок был «прыжок → декремент» вместо «декремент → прыжок». Добавили отдельный тест на `CX = 1`.

## I-5. Сегментные регистры

`cs = CS_START`, `ds = DS_START`, `ss = SS_START` - константы на все время жизни процесса, менять их из пользовательского кода нечем (`PROTECTED_REGS`), но проверка все равно висит - на случай бага в самом ядре, а не в вводе.

```python
if self.registers['cs'] != CS_START:
    errors.append(f'I-5 нарушен: CS изменён ({self.registers["cs"]} != {CS_START})')
if self.registers['ds'] != DS_START:
    errors.append(f'I-5 нарушен: DS изменён ({self.registers["ds"]} != {DS_START})')
if self.registers['ss'] != SS_START:
    errors.append(f'I-5 нарушен: SS изменён ({self.registers["ss"]} != {SS_START})')
```

**v2.5:** Появился в связке с MMU - границы сегментов теперь строятся один раз в `MMU.__init__` из этих же констант, так что их неизменность важна не только для регистров, но и для таблицы трансляции адресов.
